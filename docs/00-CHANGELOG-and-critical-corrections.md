## 1. The three findings that change the product

### 1.1 Candidate-side direct API submission is not possible (blocking)

The original Tier 5 and FR-5 assume the platform can submit applications to Greenhouse, Lever and Ashby over REST on behalf of an individual job seeker. **It cannot.** Every write path on those systems is employer-owned:

- **Greenhouse** — `POST /v1/boards/{board_token}/jobs/{id}` requires HTTP Basic Auth with the *board's* Job Board API key, issued to the employer. Greenhouse's own guidance is that these POSTs must be proxied by the integrator's own servers or the key leaks. (Note also: Harvest v1/v2 are removed after 31 Aug 2026; Harvest v3 is OAuth 2.0 only — irrelevant to job seekers, who never get a Harvest key at all.)
- **Lever** — the apply key is generated by a **Super Admin of the employer's Lever account**. Partner OAuth tokens expire hourly.
- **Ashby** — `applicationForm.submit` requires an API key carrying the `candidatesWrite` permission; Ashby documents the endpoint as the path for an employer "submitting an application as a job board."

These endpoints exist so an **employer** can build a custom careers page. A job seeker has no key and cannot obtain one. **Discovery is unaffected** — the GET endpoints are genuinely unauthenticated — but the apply half of the direct-API tier does not exist.

**Resolution:** two legitimate submission models replace it (detailed in `01`):
1. **B2B / employer-partner model** — the customer is the employer or a staffing partner who legitimately holds ATS credentials. This is the only path that supports true automated submission.
2. **User-supervised browser assist** — for a consumer job seeker, the platform pre-fills the candidate's *own* browser session under their control, using their own credentials, and the candidate presses submit.

The `DIRECT_API_SUPPORTED` capability and `AshbyAdapter.submitApplication(...)` are removed from the consumer product and retained only inside the B2B partner path.

### 1.2 The evasion layer is removed

The original Tier 5 specified JA3/JA4 TLS-fingerprint alignment, patched Chrome DevTools Protocol to defeat runtime inspection, residential proxy rotation, behavioural emulation to spoof human interaction, and a "WAF Mitigation Gateway" against Cloudflare Turnstile / DataDome / Akamai.

This is engineering whose purpose is to defeat access controls on systems the operator does not own. It is removed in full. It creates Computer Fraud and Abuse Act exposure, breaches ATS and target-site terms of service, and depends on proxy pools of questionable provenance. It is also the single largest existential risk to the business.

**Replacement stance (see `01` and `02`):** honest automation only. Real user agent, the candidate's own authenticated session, published partner APIs where they exist, conservative rate limits, and **hard stop** at any challenge — the human completes it; the system never attempts to solve or bypass it.

### 1.3 The runtime stack does not exist as written

- **Java 27 is not an LTS release.** It shipped on 15 September 2026 as the second *non-LTS* feature release after JDK 25. The current LTS is **Java 25** (released 16 September 2025).
- **Spring Boot 4.1** (latest 4.1.1, 21 Aug 2026, on Spring Framework 7.0.9, Jakarta EE 11) requires Java 17 minimum and is validated **up to and including Java 26**. "Spring Boot 4.1.x on OpenJDK 27 LTS" is therefore both mislabelled and outside the supported matrix.

**Resolution:** target **Java 25 LTS + Spring Boot 4.1.1**. Virtual threads, records, pattern matching and structured concurrency are all fully available on 25. Revisit Java 27/29 only when Boot certifies them.

## 3. What is *good* in the original and kept unchanged

The core engineering principle — **LLMs for heuristic reasoning and semantic extraction, deterministic compiled software for workflow progression, validation invariants and transaction boundaries** — is correct and is the backbone of the revision. Also retained: the multi-stage retrieval funnel (lexical → dense → RRF → cross-encoder), grounded RAG built on discrete verified achievement nodes, the human-in-the-loop approval console as the default (not the exception), event sourcing for the application lifecycle, and the evaluator–optimizer pattern for artifact generation — with the deterministic-verification addition from C-8.
